# codegraph 逐仓库建索引，跨仓库连接由我们自己按路由字面量匹配

定期巡检要对整组仓库做**跨仓库整合分析**，而全量代码进不了模型上下文
（实测三个中等仓库合计 569 万字符），必须先把每个仓库降维成结构画像。
codegraph 用于生成这份画像。它支持在任意目录跑 `codegraph init`，
因此"把整个工作区（多个仓库）当作一个项目建一张图"在操作上是成立的，且看起来正是我们要的东西——
一张图里同时有前端和后端，跨仓库关系由它自己连出来。

**我们不这么做。** 逐仓库各建一张图，跨仓库连接由 `backend/survey/crossrepo.py` 自己按 HTTP 路由字面量匹配。

## Considered Options

- **父目录一次建图，用它的跨仓库边**：最省事，跨仓库关系"免费"得到。
  实测否决 —— 见下方证据，它产出的跨仓库边 100% 是假的。
- **父目录一次建图，但只用节点、丢弃跨仓库边**：可行，但图里同时存在真边与假边且无法从边本身区分，
  任何后来者读到 `edges` 表都会自然地用它，这是个必然被踩的坑。
- **逐仓库建图，跨仓库连接自己匹配**（选中）：多写一个模块，换来"图里出现的边都是可信的"。

## 证据

在 Flutter Wonderous（Dart 30.7k 行）、NestJS（TS 132.7k 行）、gin（Go 24.1k 行）三个**彼此毫无关联**的
仓库上跑父目录单图，得到 2276 文件 / 21912 节点 / 64353 边，其中跨仓库边 824 条。
这三个仓库之间不存在任何调用关系，因此真边应为 0 —— **824 条全部是假边**：

| 源语言 → 目标语言 | 条数 |
|---|---|
| typescript → go | 520 |
| typescript → dart | 190 |
| dart → go | 61 |
| 其余 | 53 |

成因是确定的：codegraph **不索引外部依赖**，未解析的符号会被按名字连到工作区内任意同名节点上，跨语言也连。
典型案例是 Flutter 的 `debugPrint` —— 它属于 Dart SDK，不在工作区内，
而 gin 恰好也有一个 `debugPrint`，于是整张图里唯一的 `debugPrint` 定义就是那个 Go 函数：

```
repo-dart/lib/_tools/artifact_download_helper.dart :: downloadArtifacts
   --calls-->  repo-go/debug.go :: debugPrint
```

逐仓库建索引不损失任何真实信息：Dart 的跨文件边在合并图里是 1337 条（59.7%），
逐仓库建图是 1264 条（57.4%），差值正好是假边。

## Consequences

- **假边的形状恰好是我们想产出的结论。** 这是本决定的核心理由，而不是"精度略差"。
  巡检要找的正是"前端调用了后端的某个函数"这类跨仓库耦合，
  而假边长得一模一样 —— 模型拿到它们会自信地报告一堆幻觉，且读报告的人无从分辨。
  一个会产生**错误方向**噪音的信号，比没有信号更糟。

- **跨仓库连接必须自己写。** `crossrepo.py` 匹配的是 HTTP 路径字面量，是确定性的字符串比较，
  跑一万次结果一样。它只输出事实（谁调用了谁、方法是否一致、哪些接口无人调用），
  不做任何判断 —— 判断留给 L1，因为只有模型知道"字段名不一致"是不是真问题。

- **调用侧要我们自己抽。** codegraph 只抽路由的生产侧：`route` 是一等节点，还有指向处理函数的边；
  但 `fetch("/api/order/create")` 里的 URL 字面量完全不进图（`fetch` 只在 `unresolved_refs`
  留下一条 `failed`，参数丢失）。因此 `profile.extract_api_calls` 用正则补这一半。
  这不是可以省掉的冗余，是跨仓库 join 的另一条腿。

- **索引跨轮次留存并增量更新。** codegraph 只能把索引放在仓库内部
  （`CODEGRAPH_DIR` 只接受相对名，给绝对路径会被**静默忽略**，实测已确认），
  因此拉取时的 `git clean` 必须显式排除它：`git clean -fdx -e .codegraph`。
  之后走 `codegraph sync` 增量更新，实测 0.23s；索引本身也不贵（233 文件全量 245ms），
  但大仓库上这个差距会放大，而排除一个目录的成本是零。
  目录名在 `survey/common.py` 里只写一次 —— `clean -e` 与读取路径写成不同的值不会报错，
  只会让每轮拉取都把索引删掉，表现为"增量好像没生效"而日志一切正常。

- **复用索引前必须验它还能不能用。** codegraph 升级后抽取逻辑会变，沿用旧索引会让画像
  悄悄退回旧版本的水平——产出看起来完全正常，只是少了新版本才抽得出的东西。
  因此每次复用前读一次 `codegraph status -j`，`reindexRecommended` 为真或抽取版本号
  对不上就全量重建；**任何拿不准的情况都判为不可复用**，宁可多花几百毫秒。

- **codegraph 默认安装，但不是硬依赖。** 两条部署路径都会装它（版本钉死），
  装不上则警告并继续：画像退化为依赖清单级，巡检照常完成并记一条 `profile_fallback` 降级。
  代价是 L1 变成结构盲的：只知道有哪些文件，不知道有哪些接口与类型。
  `survey.codegraph_bin` 存**绝对路径** —— launchd 的 PATH 里没有 `~/.local/bin`，
  写裸名会让服务运行时找不到它，表现为每次巡检都静默降级。

- 若将来 codegraph 支持了"多根索引且跨根不做名字兜底"，本决定可以重新评估。
  重新评估的**唯一有效方式是重跑上面那组对照**，而不是读它的 release note ——
  这个行为在它的文档里从未被描述过。
