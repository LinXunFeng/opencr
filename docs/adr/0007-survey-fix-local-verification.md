# 巡检修复的本地验证不在服务端构建与运行测试

巡检修复（FixRun）在提出合并请求之前要做"本地验证"。最直接的做法是在服务端按仓库的工具链构建、跑测试。**我们没有这样做：本地验证只包括修改能否原样套用、改动范围、解释器自带解析器能检查的语法（Python、JSON），以及一次模型复核；构建与测试交给目标仓库自己的 CI。**

## Considered Options

- **在服务端构建并运行测试**：最可信，但服务要为巡检覆盖的每一种语言装齐工具链与依赖（Flutter、Gradle、Xcode、Node……），Docker 镜像会膨胀一个量级，且总有装不全的；更要紧的是，运行仓库里的构建脚本与测试，等于让任何能往被巡检仓库推代码的人在 OpenCR 的主机上执行任意命令，而这台主机持有平台令牌与模型密钥。否决。
- **每个巡检配置一条验证命令**：把工具链问题推给管理员，安全问题却原样保留；而且一条命令不可能适配组织展开出来的几十个异构仓库。否决。
- **只做不需要工具链的检查，加一次模型复核，构建与测试交给目标仓库的 CI**（选中）：合并请求本身会触发仓库 CI，那里有正确的工具链与隔离环境；OpenCR 自己的 MR 审查也会照常审查这个合并请求。

## Consequences

- 通过本地验证不代表能编译。合并请求说明、后台详情与 README 都写明"本地验证不包括构建与测试"，处理人要以 CI 为准。
- 模型复核与生成用的是同一个模型，会有同样的盲区；它只能挡住明显没解决或改坏了的修改。复核输出解析不了按未通过处理。
- 为了让套用失败能被发现，修改以"原文 → 替换文"的形式给出，原文必须在文件里恰好出现一次；不让模型输出整份新文件——长文件会被输出上限截断，截掉的代码会被静默删除。
- 以后若要加构建验证，应当在隔离的执行环境（例如一次性的容器、平台自己的 CI 流水线）里做，而不是在服务进程所在的主机上。
